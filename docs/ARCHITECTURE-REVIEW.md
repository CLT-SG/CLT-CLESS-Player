# CLESS-Player architecture review

Assessment of the Player as it exists today (v3.13.5), written to answer one
question: can this be modernised gradually, or does it require a rewrite?

**Conclusion: gradual migration is feasible, and a rewrite is not warranted.**
The reasoning is in [Verdict](#verdict). The plan that follows from it is in
[MODERNIZATION-PLAN.md](MODERNIZATION-PLAN.md).

---

## 1. What the Player is

An Electron 22 application (`index.js` main process, `preload.js` bridge) that
renders a full-screen digital-signage layout described by XML served by
CLESS-Server. The same `src/` tree is also packaged for mobile through
Capacitor (`mobile/www`), and a control panel is served on port 9000.

The renderer is a single HTML document (`src/index.html`, 454 lines of markup
plus inline boot script) that loads roughly 12,400 lines of hand-written
JavaScript as global `<script>` tags, alongside jQuery, video.js,
videojs-http-streaming, flv.js, jQuery.Marquee, pagination.js and DataTables.

| File | Lines | Responsibility |
| --- | --- | --- |
| `socketio-cpanel.js` | 4084 | Socket.IO handlers, control-panel RPC, layout/video sync |
| `slot-table.js` | 1525 | Table slot: pagination, cell decoding, live data refresh |
| `offline-layout-manager.js` | 899 | Offline layout authoring UI |
| `airport-display.js` | 774 | Airport Display events, slot overrides, announcements |
| `slot-media.js` | 757 | Images, video, HLS, FLV, YouTube |
| `activate.js` | 693 | Device registration and serial-key activation |
| `looplayout.js` | 677 | Playlist rotation and transitions |
| `layoutxml.js` | 467 | XML → DOM rendering pipeline |
| `slot-widget.js` | 509 | Widget slots |
| `slot-text.js`, `slot-tickerscrollerfader.js`, `slot-datetime.js`, `slot-html.js` | 424 | Remaining slot types |

## 2. Boot sequence

`src/index.html` runs, in order:

1. `config-loader.js` resolves `config.json` / `config.js` and fires
   `configLoaded`.
2. `getxml()` requests `<hostserver>/<id>/ds.xml`.
3. On success, `playonlineds()` parses with `xml-js` and calls `updatelayout()`.
4. On failure, `playofflineds()` reads `localStorage[dsid]`; if that is also
   empty, the document navigates to `offline.html`.
5. `playcheckNetwork()` / `keepcheckNetwork()` poll reachability;
   `setTimeout(getxml, 5000)` retries indefinitely at a fixed interval.

Two consequences matter for the migration:

- **Network-first.** The cache is consulted only after a failed request, so a
  device that is offline at boot shows nothing until the request times out.
- **Failure is a navigation.** Losing the server replaces the whole document
  with `offline.html`, tearing down all playback state; recovery is a fresh
  boot rather than a resumption.

## 3. The XML contract

Generated by `buildXML()` in the server's `core/views/main.py`. There are two
root elements.

**Single layout** — root `<Configuration>` with attributes `update`,
`serverRefresh`, `sqlQueryRefresh`, `layout`, `ds`, `mediapath`, `id`,
`schedule_id`, `sync_master_ip`. Children:

- `<display data bgcolor bgimage resolution autoscale bgscretch>`
- `<slots>` containing one element per slot, named by type: `table`, `wintv`,
  `html`, `widget`, `media`, `text`, `fader`, `ticker`, `scroller`, `date`,
  `time`, `datetime`, `bookingsystem`
- `<records>` with `<table id>` / `<row col01="…" col02="…">` sibling datasets
  for table slots

**Playlist** — root `<Configure>` with `<loop transition_style
transition_speed transition_delay>` and `<layout url duration name>` children.
Each member layout is fetched separately as its own `<Configuration>` document.

Observations:

- **Positional coupling.** The renderer addresses nodes by literal index chains
  (`result2['elements']['0']['elements']['0']['attributes']['autoscale']`). Any
  optional element the server omits shifts the indices and throws.
- **Attributes are stringly typed.** Booleans are `Y`/`N`, numbers are strings,
  and transparency is the words `high`/`medium`/`low`.
- **Overloaded cell values.** Table cells encode structure inside the string:
  `image:<w>:<h>:a.png,b.png`, `fader:One,Two`, `transition:One,Two`. The
  `image:` form is read after the *last* colon and the other two after the
  *first*, so values may themselves contain colons (`New time 18:40`).
- **Unknown elements crash.** The slot dispatch is an `if/else` chain; an
  element the build does not recognise falls through silently in some paths and
  throws in others, so the server cannot ship a new slot type before the fleet
  updates.

## 4. Rendering pipeline

`updatelayout()` → `getLayoutXML()` in `layoutxml.js`:

1. Read display attributes; if `autoscale == 'Y'`, compute a percentage scale
   per slot inline.
2. Iterate `<slots>` children through an 11-branch `if/else`, one branch per
   slot type, each building an HTML string and appending it to `#main`.
3. Slot-specific scripts then initialise behaviour by querying the DOM
   (`$('#slot-' + id)`), attaching video.js players, marquees and paginators.
4. `silentTableDataRefresh()` re-renders table bodies on the SQL refresh
   interval.

Characteristics:

- **State lives in the DOM.** The rendered markup is the model; behaviour is
  recovered by re-reading attributes and classes off elements. There is no
  in-memory representation of a slot.
- **Rebuild is total.** Any XML change re-renders `#main`, re-creating video
  elements and restarting playback, which is why `silentTableDataRefresh` and
  the "resume-layout" socket path exist as special cases.
- **Scaling is per-slot arithmetic.** `LayoutMath` in the new code found one
  real bug here: the vertical offset was divided by the layout *width*, so
  autoscaled non-square layouts drift vertically.
- **Adding a type touches many files.** A new content type requires edits to
  `layoutxml.js`, a new `slot-*.js`, `index.html` script tags, the socket
  handlers in `socketio-cpanel.js` (which enumerate slot types explicitly:
  `gettextslot`, `getmediaslot`, `gettickerslot`, `getscrollerslot`,
  `getfaderslot`, `getdateslot`, `gettimeslot`, …) and the offline manager.

## 5. Layout and playlist system

`looplayout.js` rotates playlist members with `loopTimeout`, a recursive
`setTimeout` holding `loopTimeoutDuration`. Transitions are CSS classes chosen
from a `transitionPairs` map (`fade`, `slide-left`, `slide-right`, `scroll-up`,
`scroll-down`), with a documented special case skipping the animation for
single-layout loops because it produced a visible flash.

`localStorage['currentPlayLayoutID']` records the on-screen layout, but it is
used for socket-triggered refreshes rather than for resuming after restart, so
a device reboot restarts the playlist from its first member.

## 6. Media system

`slot-media.js` selects a strategy from the source string: `{youtube:…}` braces
for embeds, `.m3u8` for HLS via videojs-http-streaming, `.flv` via flv.js,
image extensions for `<img>`, everything else for `<video>`. Library paths are
resolved relative to the `mediapath` attribute. Rotation between multiple
sources in one slot is a per-slot timer.

There is no asset versioning: media is re-requested by URL and cached only by
the Chromium HTTP cache, so a large layout can re-download unchanged video
after a cache eviction.

## 7. Scheduling

Two distinct mechanisms:

- **Clock slots** (`date`, `time`, `datetime`) each create their own recursive
  `setTimeout` in `slot-datetime.js`, formatting with a fixed server token
  vocabulary (`dd/mm/yyyy`, `HH:MM:ss`, …). A layout with several clocks runs
  several unsynchronised timers, which is visible as clocks ticking a fraction
  of a second apart.
- **Slot schedule windows** are attributes on the slot element evaluated at
  render time, including windows that wrap midnight.

Server-driven refresh uses three separate intervals from the root element:
`update`, `serverRefresh` and `sqlQueryRefresh`.

## 8. Airport Display integration

`airport-display.js` handles pushed events: it snapshots the targeted slot
(`snapshotMediaSlot`), applies a temporary override (`applyTemporaryMedia`,
`applySlotUpdate`), restores it afterwards (`restoreMediaSlot`), and plays a
multi-language announcement queue (`enqueueAnnouncement`, `pumpQueue`,
`playLanguageSequence`). It already de-duplicates by event id
(`rememberEventId`) and acknowledges with a status report (`reportStatus`).

The logic is sound; the fragility is that overrides are performed by mutating
and then restoring DOM, so a layout re-render between override and restore
loses the snapshot.

## 9. Communication

- **HTTP polling** for `ds.xml`, plus per-member requests for playlists. No
  conditional requests: every poll transfers the full document even when
  nothing changed.
- **Socket.IO** to a local sidecar (`https://localhost:9000`, backed by Pyro4
  on the server side) for `updatelayout`, `refresh-ecless`, `restart-ecless`,
  `resume-layout`, `display-change`, `display-configuration-updated`,
  `system-info-update`, per-slot getters/setters, and multi-display
  `layout-sync-broadcast` / `video-sync`.
- **Device registration** through `activate.js` with a serial key bound to the
  MAC address (`SerialKeyValidator.js`, `MultiNIC` handling).

Handlers are registered at module scope on a shared global `socket`. Because
`socket.on` is called again on reconnect paths, a redelivered event can be
applied twice.

## 10. Caching and offline

`localStorage` holds:

| Key | Contents |
| --- | --- |
| `<dsid>` | Parsed root document (single layout or loop) |
| `layout-<id>` | Parsed playlist member |
| `layout-offline-<id>` | Offline copy of a member |
| `currentPlayLayoutID` | On-screen layout id |
| `widget-cache-<widget>` | Last widget payload |

This is genuinely functional — offline playback works today — but it has no
envelope (no revision, no timestamp), no validation on read, and no eviction,
so a truncated write from a full quota is re-read and re-rejected on every
boot, and stale members accumulate.

## 11. Findings

| # | Finding | Consequence |
| --- | --- | --- |
| F1 | Positional XML access | Any new optional element in a server response can break older players |
| F2 | DOM is the model | No way to test rendering decisions without a browser; no way to reason about slot state |
| F3 | Slot dispatch is an `if/else` chain in several files | Adding a content type is a cross-cutting change, and unknown types are not forward-compatible |
| F4 | Global mutable state (`var` at module scope, shared `socket`, DOM as store) | Ownership is unclear; duplicate socket handlers cause double application |
| F5 | Network-first boot, `offline.html` on failure | Offline devices are slow to start and lose all state on a transient outage |
| F6 | No conditional requests or asset versioning | Full re-download on every poll; media re-fetched unnecessarily |
| F7 | One timer per clock and per rotation | Unsynchronised clocks; timer leaks on re-render |
| F8 | No build step, no types, no tests | Regressions are only detectable by running a device |

Two of the findings are *contract* problems (F1, F3) and must be fixed on both
sides of the wire. The rest are internal to the Player and can be fixed without
the server changing at all.

## Verdict

**A rewrite is the wrong shape for this system.** The behaviour that would be
at risk is precisely the behaviour that is hardest to re-derive: the table cell
encodings, the `Y`/`N` and `high`/`medium`/`low` attribute vocabularies, the
autoscale arithmetic, the single-layout transition suppression, the
announcement language ordering, the offline `localStorage` keys that live on
devices in the field. None of it is documented anywhere except in the code that
implements it, and much of it is depended on by deployed servers and deployed
devices simultaneously.

**Gradual migration is feasible because the coupling is concentrated at one
edge.** Everything positional and stringly typed about the legacy design is a
property of the *XML document*, not of the rendering logic. If the XML is
converted once, at the boundary, into a validated structure, then every layer
above it can be rebuilt independently and incrementally:

- The XML contract can be honoured by a single adapter module
  (`core/adapters/XmlLayoutAdapter.ts`), which is the only code that knows XML
  exists. When the last XML-only server is retired, that one directory is
  deleted and nothing else changes.
- The new renderer can be built as an additional target (`app/` → `src/app-dist`)
  without touching a line of the legacy renderer, so both ship in the same
  artifact and a device chooses one with a config flag. Rollback is a flag, not
  a release.
- The offline cache can be read from *both* schemes, so a device upgraded while
  offline keeps playing from the cache the old renderer left behind.
- Forward compatibility can be added ahead of the server: if unknown content
  types validate and degrade to a placeholder, the server is free to introduce
  new types before the fleet updates — which removes the lockstep-deployment
  problem that makes this codebase expensive to change today.

The risk that remains is behavioural drift in the adapter, and that is
addressable by testing it against fixtures taken from real `buildXML()` output
rather than by careful reading.
